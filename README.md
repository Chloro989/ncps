# centurion

小説の添削・発想支援ツール。原稿を読み込み、観点を選び、LLM に論評させ、
出力が本文と食い違っていないか機械的に検査する。

小説生成 (`write`) も含むが試作。詳細は「限界」を参照。

## 特徴

- **依存なしで動作** — 添削系は Python 標準ライブラリのみ。`pip install` 不要
- **バックエンドを選択可能** — llama.cpp / Claude API / transformers / 出力のみ
- **出力を検査** — 存在しない段落番号、本文と食い違う引用、
  原稿を指していない指摘を機械的に検出
- **ローカル完結** — Web UI は `127.0.0.1` のみ待ち受け

## 動作環境

| | |
|---|---|
| Python | 3.8 以上 |
| OS | Windows / macOS / Linux |
| GPU | 不要 (`write` と `--run` のみ必要) |

## インストール

```bash
git clone https://github.com/Chloro989/ncps
cd ncps
python main.py
```

追加パッケージは機能ごとに任意。未インストールならその機能のみ無効になる。

```bash
pip install torch transformers accelerate   # write, --run
pip install fugashi unidic-lite             # --words 形態素
```

## クイックスタート

```bash
# 1. 原稿を manuscripts/ に置く (中身は .gitignore 済み)
# 2. 構造を確認
python main.py read 原稿.txt

# 3. プロンプトを生成して任意のチャットに貼る
python main.py ask 原稿.txt --mode 発想 > prompt.txt

# 4. 得た回答を検査し、添削ファイルを出力
python main.py check answer.txt 原稿.txt --out 添削.txt
```

GUI:

```bash
python main.py web
```

## コマンド

| コマンド | 説明 | LLM |
|---|---|---|
| `web` | ブラウザ UI を起動 (`127.0.0.1:8765`)。llama-server の起動も可 | 実行時のみ |
| `read` | 原稿の章・段落・分割・反復語を表示 | 不要 |
| `ask` | 論評用プロンプトの生成と実行 | 実行時のみ |
| `check` | 回答の検査と添削ファイル出力 | 不要 |
| `write` | 小説生成 (試作) | 必須 |
| `prompts` | プロンプトの文面を `prompts/` に書き出す | 不要 |
| `test` | テスト実行 (872 件) | 不要 |

`read` / `ask` / `check` は同一のパーサを共有する。

# 使い方

## 原稿の指定

```bash
python main.py read 原稿.txt          # manuscripts/ 内はファイル名のみで可
python main.py read C:\path\to\原稿.txt
python main.py read                   # 省略時はファイル選択ダイアログ
```

Colab ではダイアログの代わりにアップロード UI が開く。
`manuscripts/` の内容は `.gitignore` で除外済み。

対応形式:

- 文字コード: UTF-8 / Shift_JIS / EUC-JP を自動判別
- 章見出し: `# 見出し` / `第一章` / `＊` などの区切り行
- 青空文庫形式: 凡例・底本・ルビ・傍点注記を除去し、題名と著者を抽出
- 段落: 空行区切りと 1 行 1 段落の両方

## 構造の確認

```bash
python main.py read 原稿.txt --size 3000
```

```
「冒頭プロトタイプ 第五稿」

3000文字ずつに切ると 2塊
  塊0: 0章 段落0〜70 (2977文字)
  塊1: 0章 段落71〜102 (1587文字、うち重なり1段落)

反復 11件

  《主題》「田島」[3]・[4]・[7]・[14]…他4箇所 (隔たり96%・4201文字)
```

- **主題** — 作品全体に分布する語

## 論評の実行

バックエンドは 4 種類。

### 出力のみ (既定)

```bash
python main.py ask 原稿.txt --mode 発想 > prompt.txt
python main.py check answer.txt 原稿.txt --out 添削.txt
```

LLM を呼ばずプロンプトのみ出力する。任意のチャットに貼り付けて使う。

### Claude API

```bash
setx ANTHROPIC_API_KEY "sk-ant-..."     # Windows。設定後に端末を再起動
python main.py ask 原稿.txt --api --out 添削.txt
python main.py ask 原稿.txt --api --all --out 添削.txt   # 全塊を処理
```

API キーは環境変数から読み取るのみ。保存・表示は行わない。

### llama.cpp

AMD GPU で動作する唯一のバックエンド (torch は非対応、llama.cpp は Vulkan 対応)。

```bash
winget install ggml.llamacpp
llama-server --list-devices              # GPU 認識の確認
llama-server -hf LiquidAI/LFM2.5-1.2B-JP-202606-GGUF -ngl 99 -c 16384 --port 8080
```

```bash
python main.py ask 原稿.txt --llama --model LFM2.5-1.2B-JP
```

- `-ngl 99` — 全レイヤーを GPU に配置
- `-c 16384` — コンテキスト長。既定の 4096 では不足する

**制約:** `llama-server` は起動時に読み込んだモデル 1 つのみを提供する。
`--model` はサーバに送信されるが**無視される**ため、記録用のラベルとして機能する。
複数モデルを使う場合はポートを分けてサーバを複数起動する。

### ブラウザ UI から起動する

`python main.py web` の**サーバータブ**から、
起動・停止・起動ログの確認ができる。端末を分ける必要はない。

タブ構成は左から `サーバー` / `添削` / `創作` / `チャット`。

| 項目 | 内容 |
|---|---|
| 載せるモデル | キャッシュを走査した一覧から選択 |
| 名前を直に書く | 未取得のモデルはここに書けば取得して起動 |
| GPU に載せる層 | `-ngl` |
| CPU に置くエキスパート | `--n-cpu-moe` (MoE のみ) |
| 文脈の長さ | `-c` |
| Flash Attention と KV 8bit 化 | `-fa on --cache-type-k/v q8_0` |
| ポート | `--port` |

モデル名から MoE か密かを判定し、どちらのつまみを回すべきか表示する。
起動後は `load_tensors:` を含む起動ログをそのまま確認できる。

起動したポートは論評の送信先に自動で反映される。
UI を終了すると起動した `llama-server` も停止する。

**起動できる対象の制限:** シェルを経由せず引数は配列で渡す。
モデル名はキャッシュで検出したものか、
`組織/名前:量子化` の形式に一致するもののみ受け付ける。
数値引数は整数に変換して範囲内に丸める。
`--host` は `127.0.0.1` に固定する。

```
a; whoami        → 拒否
../../etc/passwd → 拒否
-ngl 999999      → 999 に丸める
```

起動失敗時はログから原因を判定して表示する。

| ログ中の文字列 | 表示 |
|---|---|
| `failed to open GGUF file` | `-hf` と `-m` の取り違え |
| `out of memory` | `-ngl` または `-c` を減らす |
| `unknown argument` | llama.cpp のバージョンが古い |

### 解析結果のキャッシュ

一度読んだ原稿と、その解析 (段落分割・実測・反復語) を保持する。
同じ原稿を読み直す際に再解析しない。

```
1 回目  174ms  (cached: false)
2 回目    3ms  (cached: true)
```

重いのは反復語の探索で、形態素解析を有効にするとさらに時間がかかる。

キャッシュキーは以下の要素で構成する。いずれかが変われば再解析する。

| 対象 | キー |
|---|---|
| ファイル | 絶対パス + 更新時刻 + サイズ |
| 貼り付け | 本文の SHA-256 (先頭 16 文字) |
| 共通 | 分割サイズ、語の取り出し方 |

原稿を書き換えれば更新時刻が変わるため、自動で再解析される。
上限は 24 件。超えると古いものから破棄する (LRU)。

サーバータブの「覚えているもの」で件数とヒット率を確認でき、
「忘れる」で全て破棄できる。

**LLM の応答はキャッシュしない。** 同じプロンプトでも出力は毎回変わるべきで、
キャッシュすると「2 回目も同じ応答が返る」ことに気付けなくなる。
キャッシュ対象は原稿から機械的に決まる値のみ。

```bash
python main.py ask --models
```

```
llama-server (http://127.0.0.1:8080/v1/chat/completions)
  載っているのは unsloth/Qwen3.8-27B-GGUF:Q4_K_M

置き場
  C:\Users\darki\.cache\huggingface\hub

落ちている GGUF 5件
  → unsloth/Qwen3.8-27B-GGUF:Q4_K_M (15.9GB)
    unsloth/Qwen3.6-35B-A3B-GGUF:UD-Q4_K_M (20.6GB)
    LiquidAI/LFM2.5-1.2B-JP-202606-GGUF:Q4_K_M (0.7GB)
```

`→` が現在サーバに載っているもの。表示名はそのまま `-hf` に渡せる。

- **載っているモデル** — `/v1/models` に問い合わせて取得。
  `--model` はサーバに無視されるため、これが唯一の確実な情報源
- **落ちている GGUF** — キャッシュを走査。書き並べた一覧ではない
- `mmproj-*.gguf` (画像入力用) と分割ファイルの 2 個目以降は除外

キャッシュの場所は環境変数と OS から判定する。

| 優先 | 場所 |
|---|---|
| 1 | `~/.cache/huggingface/hub` (現行の llama.cpp) |
| 2 | `$HF_HOME/hub` |
| 3 | `$LLAMA_CACHE` |
| 4 | `%LOCALAPPDATA%\llama.cpp` / `~/.cache/llama.cpp` (旧版) |

ブラウザ UI のモデル選択欄も同じ情報で埋まる。

添削ファイルの `モデル` 欄には、サーバに問い合わせた名前を記録する。
`--model` の申告と食い違う場合は両方を残す。

```
# モデル: unsloth/Qwen3.8-27B-GGUF:Q4_K_M (llama.cpp が申告) ※--model には Qwen と書かれていた
```

問い合わせに失敗した場合は `(llama.cpp・名前は未確認)` と記録する。

### モデルの指定

`-hf` と `-m` は別物。

| フラグ | 引数 | 例 |
|---|---|---|
| `-hf` | HuggingFace のリポジトリ名 | `-hf unsloth/Qwen3.8-27B-GGUF:Q4_K_M` |
| `-m` | ローカルのファイルパス | `-m C:\models\model.gguf` |

`-m` にリポジトリ名を渡すと `failed to open GGUF file` になる。

リポジトリには複数の量子化が入っているため、`-hf` では
`:Q4_K_M` のように量子化名を付ける。省略すると既定が選ばれる。

### VRAM に収まらないモデル

`-ngl 99` は全レイヤーを GPU に置く指定。VRAM を超えると起動失敗、
または極端に低速になる。収まらない場合は CPU との分割が必要。

```bash
llama-server -hf unsloth/Qwen3.8-27B-GGUF:Q4_K_M --port 8081 \
  -ngl 36 -fa on --cache-type-k q8_0 --cache-type-v q8_0 -c 12288
```

| フラグ | 効果 | 適用範囲 |
|---|---|---|
| `-ngl N` | GPU に置くレイヤー数。残りは CPU | 全モデル |
| `-fa on` | Flash Attention。KV キャッシュの量子化に必要 | 全モデル |
| `--cache-type-k/v q8_0` | KV キャッシュを 8bit 化。使用量が約半分 | 全モデル |
| `--n-cpu-moe N` | エキスパートのみ CPU に置く | **MoE のみ** |
| `-ot "正規表現=CPU"` | 特定テンソルを CPU に置く | 全モデル |

`--n-cpu-moe` は MoE モデルにしか効かない。
密なモデルに指定しても無視される。
MoE かどうかはモデル名で判別できる (`A3B` = 活性 3B の MoE)。

起動ログの `load_tensors:` 行で各デバイスへの配分量を確認できる。
`-ngl` を 4〜8 ずつ増減させて、VRAM に収まる最大値を探す。

### 12GB クラスの GPU でのモデル選択

| モデル | 種別 | Q4_K_M | 12GB での挙動 |
|---|---|---|---|
| 27B 密 | dense | 約 16.5GB | 4 割を CPU。2〜4 tok/s |
| 35B-A3B | MoE | 約 21GB | エキスパートを CPU。10〜20 tok/s |
| 8B 密 | dense | 約 5GB | 全て GPU。30 tok/s 以上 |

MoE は総パラメータが大きくても活性パラメータが少ないため、
エキスパートを CPU (RAM) に置いても速度低下が小さい。
VRAM が限られる環境では、同じ待ち時間でより大きなモデルを使える。

CPU 分割時は生成速度が大きく低下するため待ち時間を延長する。

```bash
python main.py ask 原稿.txt --llama --llama-timeout 7200
```

既定は 3600 秒。実行後に `1240秒で3812トークン (3.1 tok/s)` が表示される。

`write` の抑圧処理はロジット操作を必要とするため llama.cpp では動作しない。
論評系は抑圧を使わないので影響しない。

### transformers

NVIDIA GPU が必要。

```bash
python main.py ask 原稿.txt --run
python main.py ask 原稿.txt --run --model LiquidAI/LFM2-1.2B
```

`transformers` 5.14 は LFM2 系 (`lfm2` / `lfm2_moe` / `lfm2_vl`) に対応済み。

| `--api` | 不要 | 従量 | 最も高品質 |

## 添削ファイル

`--out` で出力。ヘッダに実行条件、本文に段落ごとの指摘が並ぶ。

```
# 原稿名 の添削
# 日付: 2026-08-15 21:56
# モード: 発想
# モデル: claude-sonnet-5 (API)
# 原稿: 5782文字 / 104段落
# 読ませた範囲と観点: 1/1塊 一度きり／固有／分岐 [実測 名前25% …]
# 検証: claude-opus-5 (API) — 6件を残し、8件を捨てた
# 語の取り出し: 正規表現
# 原稿を指している指摘 12/14件 (86%)
# 引用の照合: 14件中 一致12件 / 不一致2件

## 本文と指摘

[58] アパートに帰り、電気もつけずに、私は部屋の真ん中に立っていた。
    × - **段落 [58]**: 「エーマートの前を通った。半分切れた看板が…」
```

| 記号 | 意味 |
|---|---|
| `▸` | 引用が本文と一致。採用可 |
| `×` | 引用が本文と不一致。破棄すべき |

`モデル` 欄はバックエンドにより表記が変わる。

| 実行方法 | 記録 |
|---|---|
| `--api` | `claude-sonnet-5 (API)` |
| `--llama` | `unsloth/Qwen3.8-27B-GGUF:Q4_K_M (llama.cpp が申告)` |
| `--run` | `Qwen/Qwen2.5-3B-Instruct (手元)` |
| `check` | `不明 (外で解かせた答え)` |
| `check --model NAME` | `NAME (申告)` |

# モードと観点

## モード

| `--mode` | 処理内容 | 制約 |
|---|---|---|
| `発想` | 未着手の可能性を提示させる (既定) | — |
| `査読` | 観点を回して客観的に論じさせる | `--severity` が効く |
| `採点` | 7 観点のルーブリックで 5 段階評価させる | `--severity` が効く |
| `接続` | 離れた 2 箇所の関連付けを提案させる | 3000 文字以上 |
| `連想` | 連想を辿り作品に還元させる | — |

`接続` は距離のある 2 点を必要とするため、短編では実行を拒否する。

`査読` と `採点` の違いは出力の形式。`査読` は観点ごとの自由記述、
`採点` は固定 7 観点の点数と根拠。`採点` は観点を選ばないため
`--lens` `--lenses` `--random-lenses` は無視される。

## 厳しさ

`査読` と `採点` の基準を 3 段階から選ぶ。既定は `標準`。

```bash
python main.py ask 原稿.txt --mode 査読 --severity 育成
python main.py ask 原稿.txt --mode 採点 --severity 厳格
```

| `--severity` | 想定読者 | 基準の置き方 |
|---|---|---|
| `育成` | 初心者〜アマチュア | 評価 3 = アマチュアとして十分健闘 / 5 = 商業出版に手が届く |
| `標準` | 一般 (既定) | 評価 3 = 破綻なく機能している一般的な水準 |
| `厳格` | 商業投稿・公募 | 評価 1 = 商業出版可能な一般的作品 / 5 = 文学史に残りうる |

厳しさは規則そのものを差し替える。

| | `育成` | `標準` | `厳格` |
|---|---|---|---|
| 良い点の扱い | 必ず先に挙げる | 問題点と同じ精度で | 加点理由にならない |
| 改善点の数 | 優先度の高いものに絞る | 制限なし | 制限なし |
| 迷ったとき | — | — | 必ず低い方を選ぶ |
| 比較対象 | 書き手の現在地 | 一般的な水準 | 商業出版水準 |

`厳格` で全項目 1 点は「商業水準に達している」という意味であり、
低評価ではない。基準の置き方が違うだけなので、
`育成` と `厳格` の点数を並べて比較することはできない。

`発想` `接続` `連想` では `--severity` は無視される
(添削ファイルの記録にも書かない)。

## 採点の観点

| # | 観点 |
|---|---|
| 1 | 構成・プロット |
| 2 | キャラクター |
| 3 | 文章・文体 |
| 4 | 描写 |
| 5 | 対話 |
| 6 | テーマ・主題 |
| 7 | 世界観・設定 |

合計 35 点。各観点について評価点・判定理由・本文からの根拠を出力させる。
出力形式は厳しさによって変わる (`育成` は「次の一歩」を含む)。

### 点数の検算

採点モードでは出力を機械的に検算する。引用の照合と同じく、
本文を読まずに確認できる項目のみを対象とする。

| 検査 | 出力例 |
|---|---|
| 合計点の一致 | `合計が合わない。書かれた合計は16点だが、各観点の和は30点` |
| 観点の欠落 | `抜けている観点 3件: 対話、テーマ・主題、世界観・設定` |
| 点数の範囲 | `描写 が範囲外の 7点` |
| 合計点の記載 | `合計点が書かれていない` |
| 形式の逸脱 | `採点の形になっていない` |

LFM2.5-1.2B で実測: 4+3+5+5+4+5+4 = 30 に対し `合計点 16/35` と出力された。
結果は `--out` の添削ファイルのヘッダにも記録される。
検算に引っかかった場合、終了コードは 1 になる。

### 分割時の注意

採点は作品全体への評価だが、既定では先頭の塊のみを渡す。
原稿が分割された状態で採点を実行すると警告する。

```
# 注意: 5つに分けたうちの1つ目だけを採点している。作品全体の点数ではない。
#   全体を見せるなら --size 6074 以上にするか、--all で塊ごとに採点すること
```

## プロンプトの編集

規則・観点・ルーブリックの文面はすべて `prompts/` に書き出して編集できる。

```bash
python main.py prompts                 # 既定の文面を prompts/ に書き出す
python main.py prompts --force         # 既定値で上書きする
python main.py prompts --dir 別置き場   # 別の場所に書き出す
```

| ファイル | 内容 |
|---|---|
| `発想.txt` | 発想モードの役割と規則 |
| `査読-育成.txt` `査読-標準.txt` `査読-厳格.txt` | 査読モードの役割と規則 |
| `採点-育成.txt` `採点-標準.txt` `採点-厳格.txt` | 採点モードの役割と規則とルーブリック |
| `観点.txt` | 観点の一覧 |

`prompts/` に該当ファイルがあればそちらが使われ、なければ組み込みの既定値が
使われる。ファイルを削除すれば既定値に戻る。
別の場所を使う場合は `--prompts 置き場` を渡す。

```bash
python main.py ask 原稿.txt --mode 査読 --prompts 実験用/
```

`観点.txt` は 1 行 1 観点で、縦棒区切り。

```
キー | 群 | 使えるモード | 問い
```

```
削除 | 構造 | 発想,査読 | この範囲から一つの場面か人物か段落を消したとき、何が壊れるかを述べよ。
手作り | 実験 | 査読 | 自分で足した観点。
```

`#` で始まる行と空行は無視する。書式が壊れていれば行番号つきでエラーになる。

`prompts/` を編集した状態で実行すると、添削ファイルに
どのファイルを使ったかが記録される。

## 観点の選択

観点は 28 種類 (発想 21 / 査読 13)。既定では原稿を測定し、不足している要素に対応する観点を選ぶ。

```bash
python main.py ask 原稿.txt --survey            # 測定値と選択理由を表示
python main.py ask 原稿.txt --lens 視点,熱量     # 手動指定
python main.py ask 原稿.txt --random-lenses     # ランダム選択
python main.py ask 原稿.txt --lenses 2          # 個数変更 (既定 3)
```

観点はモードによって使えるものが異なる。

| 群 | 観点 | 発想 | 査読 |
|---|---|---|---|
| 構造 | 削除・重心 | ○ | ○ |
| 構造 | 順序・一度きり | ○ | — |
| 逸脱 | 予想・安全・約束事・既視 | ○ | — |
| 視点 | 視点・時制・信頼 | ○ | — |
| 不在 | 分岐・沈黙・欠落 | ○ | — |
| 熱量 | 密度 | ○ | ○ |
| 熱量 | 熱量 | ○ | — |
| 調子 | 調子・笑い・落差 | ○ | ○ |
| 具体 | 固有・感覚 | ○ | — |
| 査読 | 主題・構成・文体・人物・仕掛け・達成・未達 | — | ○ |

**査読モードでは提案型の観点を使わない。** 査読の規則は
「本文に無い要素について述べない」であり、
「書かれなかった道を三つ挙げよ」のような観点と矛盾するため。
`--lens` で明示指定した場合もモード不適合ならエラーになる。

**個数は 3 以下を推奨。** 3B 級モデルでは指示数に反比例して各指示の遵守率が
低下する (禁止語 6 個では有効、8 個では逆効果という測定結果)。
広く見る場合は個数を増やさず `--all` または `--seed` を変えて複数回実行する。

### 測定値

`--survey` で表示される値。すべて 0〜1 に正規化。

| 項目 | 内容 |
|---|---|
| 名前 | 固有名詞を含む段落の割合 |
| 会話 | 会話文の段落の割合 |
| 出来事 | 過去の出来事を 2 文以上含む段落の割合 |
| 感覚 | 使用されている感覚の種類 (音・におい・手触り・温度・光) |
| 一人称 | 一人称代名詞を含む段落の割合 |
| 偏り | 段落長の変動係数 |
| 混在 | ですます体とである体の混在度 |
| 轍 | 常套語 (宇宙・神秘・永遠 等) の密度 |

観点の必要度はこれらから算出する。例: 名前が少なければ【固有】が上昇し、
感覚が揃っていれば【感覚】が下降する。

## 語の抽出方法

反復語検出時の単語分割方法。

```bash
python main.py read 原稿.txt --words 形態素     # fugashi + unidic-lite が必要
```

| 方式 | 依存 | 特性 |
|---|---|---|
| 正規表現 (既定) | なし | 漢字 2 文字以上 / カタカナ 2 文字以上 |
| 形態素 | fugashi, unidic-lite | 1 文字の名詞を検出。複合語が分割される |

既定を正規表現にしている理由は測定結果による。形態素解析に置換すると
検出数が 68 → 178 件に増加し (副詞などのノイズ)、
複合語「虫干し」が「虫 / 干し」に分割され既知の伏線を取りこぼした
(正解率 4/7 → 3/7)。ただし 1 文字名詞が取れる利点はある。

不要と判断した場合は `centurion/connect.py` の `morphological_words` を削除する。

# 出力の検査

LLM 出力は信頼しない前提で設計している。`--api` / `--run` / `--llama` 実行時は
自動、貼り付け運用時は `check` で実行する。

```bash
python main.py check answer.txt 原稿.txt --chunk 1 --out 添削.txt
```

## 検査項目

| 項目 | 検出内容 |
|---|---|
| 錨の数 | 原稿のどの段落も指していない指摘の割合 |
| 段落番号 | 存在しない段落番号への言及 |
| 範囲外 (`--chunk N`) | 入力に含めていない段落への言及 |
| 引用照合 | 段落番号と引用文の不一致、本文に存在しない引用 |

### 錨の数

引用照合は引用を含む指摘しか検査できない。段落を一切指さない出力は
検査を素通りし「不一致 0 件」と表示されてしまう。

実測例: 4 件の指摘がいずれも段落を指さず、本文に存在しない語のみで
構成されていたが、引用照合は「1 件中 一致 1 件」を出力した。

```
原稿を指している指摘 0/4件 (0%)
  半分も原稿を指していない。本文から離れた一般論になっている疑いが強い。
  観点を減らすか、より大きいモデルに解かせること
```

### 引用照合

10 文字以上の鉤括弧のみを照合対象とする。日本語では作中語を
「あっちゃぐり」のように括る用法が一般的で、短い括弧まで照合すると
正当な指摘に `×` が付く (実測で 4 件中 3 件が誤検出)。

実測例 (Qwen2.5-3B):

```
× [58] 引用は [57] の中身: エーマートの前を通った。半分…
× [59] 本文に無い文を引用している: 帰る途中、エーマートの冷蔵庫…
```

段落番号は 18 件すべて実在したが、引用 14 件中 8 件が別段落の内容であり、
うち 3 件は本文に存在しない文だった。
「引用が実在するか確認せよ」とモデルに自己申告させる方式では検出できない。

## 検証 (LLM による再審査)

```bash
python main.py ask 原稿.txt --llama --verify
python main.py ask 原稿.txt --llama --verify --verify-with api
python main.py ask 原稿.txt --api --verify --verify-model claude-opus-5
```

| 引数 | 既定 | 説明 |
|---|---|---|
| `--verify` | — | 出力された指摘を再審査し、通過分のみ残す |
| `--verify-with` | 同一 | 審査側のバックエンド (`api` / `llama` / `run`) |
| `--verify-model` | 同一 | 審査側のモデル |
| `--verify-llama-url` | `--llama-url` と同一 | 審査側の llama-server |

機械的検査では「引用は正しいが判断が誤り」を検出できないため、
別モデルによる再審査を行う。

設計方針:

- **二値判定。** 点数評価は基準が実行ごとに 19pt 変動する測定結果があるため、
  「残す」「捨てる」のみを選択させる
- **反証側に立たせる。** 肯定的評価を求めると全件通過するため、
  欠陥を探す役割を与え、判断に迷う場合は破棄を既定とする
- **別モデルを推奨。** 同一モデルは自身の出力を通過させる傾向がある

破棄基準: 本文に存在しない内容 / 誤読 / 実行不可能な助言 /
代償の未記載 / 他の指摘との重複。

安全機構:

- 全件破棄された場合は元の出力を保持する (審査側の過剰動作を疑う)
- 判定不能だった指摘は破棄せず印を付けて残す
- 判定が 1 件も読み取れない場合は元の出力をそのまま返す

### llama.cpp で別モデルを使う場合

`llama-server` は 1 プロセスにつき 1 モデルのみ提供する。
`--verify-model` に別名を指定してもサーバは無視するため、
**同一 URL を指す限り審査は同じモデルが行う。**

別モデルで審査するにはポートを分けてサーバを 2 つ起動する。

```bash
llama-server -hf LiquidAI/LFM2.5-1.2B-JP-202606-GGUF -ngl 99 --port 8080
llama-server -hf Qwen/Qwen2.5-7B-Instruct-GGUF -ngl 99 --port 8081
```

```bash
python main.py ask 原稿.txt --llama --verify --verify-llama-url http://127.0.0.1:8081/v1/chat/completions
```

同一 URL を指している場合は実行時に警告を出す。

# 限界

## 小説生成

「発想の飛躍」は未達成。出力は可読で常套からわずかに外れた文章であり、
飛躍ではない。3 機構を実装・測定していずれも読み手に差を検出できなかった。

実測 112 件の分析:

| 項目 | 割合 |
|---|---|
| 読み手に語りかける | 112/112 (100%) |
| 固有名詞を含む | 2/112 (2%) |
| 過去の出来事を 2 文以上語る | 32/112 (29%) |
| 一文目が「X は〜です」型の一般論 | 47/112 (42%) |

人格設定は「物語だけを愛する」だが 7 割が出来事を語っていない。
原因は書き出しの `そうですね、` と推定 (相槌の後に続く自然な文型は
同意・意見・一般化であり、場面描写ではない)。**未検証**のため
既定は評価時と同じ値のまま。`--prefill` で変更可能。

流動プロンプトの優位性は p=0.108 で有意水準未達。`--fixed-prompt` で戻せる。

## 添削

3B 級モデルでは実用に耐えない。実測:

- 引用 14 件中 8 件が別段落の内容、うち 3 件は本文に存在しない文
- 別の実行では 4 件の指摘がいずれも段落を指さず、本文にない語のみで構成

検査機構はこれらを検出するが、検出できても出力の質は上がらない。
実用には API または 7B 以上のモデルを推奨。

## 接続モード

3000 文字未満の原稿では動作しない。距離のある 2 点が存在しないため。
実測: 太宰治「I can speak」(1949 文字・15 段落) では、
段落間距離 27% と表示された語が実際には 4 段落しか離れておらず、
同一場面の同一人物を指していた。距離の下限を 1500 文字に設定して対処。

## 語の抽出

- 1 文字の語を検出できない (形態素解析未使用時)
- 固有名詞判定は敬称・地名接尾辞・4 文字以上のカタカナによる近似
- 「一度きりの語」は長編でのみ有効 (4500 文字では 221 語が該当)
