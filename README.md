# センチュリオン

小説を書く人に伴走する道具と、文章を保ったまま常套から外れた語りを返す生成AI。

操作はすべて `main.py` から。

| 命令 | すること | モデル |
|---|---|---|
| `web` | **ブラウザから使う** | 解かせるときだけ |
| `read` | 原稿の構造・反復を見る | 不要 |
| `ask` | 原稿を読ませて論評・発想を得る | 解かせるときだけ |
| `check` | 答えが本文と食い違っていないか検査する | 不要 |
| `write` | 小説を書かせる | 必要 |
| `test` | 試験を全部走らせる(537件) | 不要 |

```bash
python main.py web
```

ブラウザが開く。原稿を選び、モードと観点を決めて、実行を押すと
本文の下に指摘が並ぶ。引用が食い違う指摘は赤くなる。
以下は同じことを端末からする手順。

# 使い方

## 1. 用意する

```bash
git clone https://github.com/Chloro989/ncps
cd ncps
python main.py
```

**原稿を読ませるだけなら、これで動く。** Python 3.8以降があればよく、
`pip install` も仮想環境も要らない(`read` `ask` `check` `test` は
標準ライブラリだけで動く)。

追加が要るのは次の2つだけ。

| したいこと | 要るもの |
|---|---|
| 小説を書かせる (`write`) | `pip install torch transformers accelerate` |
| 反復を形態素で探す (`--words 形態素`) | `pip install fugashi unidic-lite` |

どちらも入れなければ、その機能だけが使えず、他は動く。
試験も入っていない分は自動で飛ぶ。

## 2. 原稿を置く

`manuscripts/` に入れる。**この中身は git に入らない**ので、
未発表の作品を置いても公開リポジトリには出ない。

```bash
python main.py read 第五稿.txt
```

パスを省くと窓が開く。手元のPCならファイル選択、Colab ならアップロード。

```bash
python main.py read
```

## 3. まず原稿を見る

```bash
python main.py read 第五稿.txt
```

```
「冒頭プロトタイプ 第五稿」
  4533文字 / 1章 / 103段落 / 218文

3000文字ずつに切ると 2塊
  塊0: 0章 段落0〜70 (2977文字)
  塊1: 0章 段落71〜102 (1587文字、うち重なり1段落)

反復 11件
  《反復》「航空研究会」[3]・[71] (隔たり66%・2715文字)
  《主題》「田島」[3]・[4]・[7]・[14]…他4箇所 (隔たり96%・4201文字)
```

「反復」は遠く離れて繰り返される稀な語 = 作者がすでに植えた種。
「主題」は作品を貫く背骨。

## 4. 論評させる

道は四つある。**質が要るなら 4-A、無料で済ませたいなら 4-B、
手元のGPUで回したいなら 4-C。**

### 4-A. その場で論評させる (鍵が要る)

```bash
python main.py ask 第五稿.txt --mode 発想 --api --out 添削.txt
```

鍵は一度だけ設定する。この道具は保存も表示もしない。

```bash
setx ANTHROPIC_API_KEY "自分の鍵"        # Windows。設定後に端末を開き直す
```

```python
import os; os.environ['ANTHROPIC_API_KEY'] = '自分の鍵'   # Colab
```

原稿全体を順に読ませるなら `--all`。塊ごとに観点が入れ替わる。

```bash
python main.py ask 第五稿.txt --mode 発想 --api --all --out 添削.txt
```

### 4-B. 問いだけ出して、好きなチャットに貼る (無料)

```bash
python main.py ask 第五稿.txt --mode 発想 > 問い.txt
```

`問い.txt` を Claude なり ChatGPT なりに貼り、答えを `答え.txt` に保存してから

```bash
python main.py check 答え.txt 第五稿.txt --out 添削.txt
```

### 4-C. 手元の llama.cpp で解かせる (無料、AMDのGPUでも動く)

**手元にAMDのGPUしかないなら、これが唯一のGPUの道。**
torch は RX 6700 XT を使えないが、llama.cpp は Vulkan で使える。

はじめに llama.cpp を入れる(一度だけ)。入れたら端末を開き直す。

```bash
winget install ggml.llamacpp
```

GPU が見えているかを確かめる。`RX 6700 XT` が出れば成功。
出なければ CPU 版なので、[llama.cpp のリリース](https://github.com/ggml-org/llama.cpp/releases)から
`llama-*-bin-win-vulkan-x64.zip` を落として展開する。

```bash
llama-server --list-devices
```

別の窓でサーバを立てる。初回はモデルの取得で数分かかる。

```bash
llama-server -hf LiquidAI/LFM2.5-1.2B-JP-202606-GGUF -ngl 99 -c 16384 --port 8080
```

- `-ngl 99` … 全部の層を GPU に載せる
- `-c 16384` … 文脈の広さ。原稿6000文字と答え4000トークンで、既定の4096では足りない

この窓は開けたまま、別の窓でセンチュリオンを動かす。

```bash
python main.py ask 第五稿.txt --mode 発想 --llama --model LFM2.5-1.2B-JP
```

| 引数 | 既定 | 意味 |
|---|---|---|
| `--llama` | — | 立ててある llama-server に解かせる |
| `--llama-url` | `http://127.0.0.1:8080/v1/chat/completions` | サーバの窓口 |

`--model` はここでは**記録のためだけ**に使う(どのモデルを載せたかは
サーバ側で決まっているため)。添削ファイルに `(llama.cpp)` として残る。

日本語特化の [LFM2.5-1.2B-JP-GGUF](https://huggingface.co/LiquidAI/LFM2.5-1.2B-JP-202606-GGUF)
のほか、GGUF ならどれでも載せられる。

**注意:** llama.cpp ではロジットに手を入れられないので、
小説を書かせる側 (`write`) の抑圧は使えない。論評では抑圧を使っていないため、
こちらは問題にならない。

### 4-D. 手元の transformers で解かせる (NVIDIAのGPUが要る)

```bash
python main.py ask 第五稿.txt --mode 発想 --run
python main.py ask 第五稿.txt --mode 発想 --run --model LiquidAI/LFM2-1.2B
```

`--model` には HuggingFace のどのモデル名でも渡せる。
`transformers` 5.14 は LiquidAI の LFM2 系(`lfm2` / `lfm2_moe` / `lfm2_vl`)に
対応済みなので、追加の作業なしで動く。

小さいモデルでは**引用14件中8件を取り違えた**実測がある(Qwen2.5-3B)。
下の「検査」を必ず通すこと。

## 5. 添削を受け取る

`--out 添削.txt` を付けると、本文の各段落の下にその段落あての指摘が並ぶ。

先頭に**何をどう読ませた添削なのかが残る**。溜まった添削を並べて
比べるとき、モードとモデルが分からないと比較にならないため。

```
# あっちゃぐり の添削
# 日付: 2026-08-12 13:31
# モード: 発想
# モデル: claude-sonnet-5 (API)
# 原稿: 5782文字 / 104段落
# 読ませた範囲と観点: 1/1塊 一度きり／固有／分岐 [実測 名前25% / 会話32% …]
# 語の取り出し: 正規表現
# 引用の照合: 14件中 一致6件 / 不一致8件
# うち3件は本文に無い文の引用。× の付いた指摘は捨てること
```

モデルの欄は解かせ方で変わる。

| 解かせ方 | 記録 |
|---|---|
| `--api` | `claude-sonnet-5 (API)` |
| `--llama` | `LFM2.5-1.2B-JP (llama.cpp)` |
| `--run` | `Qwen/Qwen2.5-3B-Instruct (手元)` |
| `check`(外で解かせた答え) | `不明 (外で解かせた答え)` |
| `check --model 名` | `名 (申告)` — 何に解かせたかを自分で記録できる |

そして本文と指摘。

```
[57] 帰り道、エーマートの前を通った。半分切れた看板が「ー マート」と光っている。

[58] アパートに帰り、電気もつけずに、私は部屋の真ん中に立っていた。
    × - **段落 [58]**: 「エーマートの前を通った。半分切れた看板が…」
```

`×` が付いた指摘は**引用が本文と食い違っている**ので捨てる。
`▸` が付いたものは照合を通っている。

# モードと観点

## モード (`--mode`) — 自分で選ぶ

| モード | 何をさせるか | 向く原稿 |
|---|---|---|
| `発想` | まだ書かれていない先を探させる (既定) | どれでも |
| `査読` | 客観的に評価・査読させる | どれでも |
| `接続` | 遠く離れた二箇所に橋を架けさせる | **3000文字以上** |
| `連想` | 連想を数歩たどって作品へ戻させる | どれでも |

`接続` は遠い二点が要るので短編では断られる。そのときは `発想` を使う。

## 観点 — 既定では原稿を測って選ぶ

観点は18個ある(視点・熱量・削除・分岐・固有・感覚…)。
**既定では原稿を実測して、足りていないところへ問いを向ける。**
感覚描写で埋まった原稿に「感覚を足せ」と言っても意味がないため。

何が測られ、どの観点が選ばれるかを見る:

```bash
python main.py ask 第五稿.txt --survey
```

```
実測
  名前のある人や場所を含む段落        25%
  過去の出来事を2文以上語る段落       27%
  使われている感覚の種類            100%

観点の必要度
   75%  【一度きり】構造
   75%  【固有】具体
   73%  【分岐】不在
   ...
   14%  【感覚】具体          ← 感覚は足りているので選ばれない
```

**観点を自分で決めることもできる。**

```bash
python main.py ask 第五稿.txt --lens 視点,熱量,安全      # 名指しする
python main.py ask 第五稿.txt --random-lenses           # くじ引きに戻す
python main.py ask 第五稿.txt --lenses 5                # 数を変える(既定3)
```

使える観点の名前:

| 群 | 観点 |
|---|---|
| 構造 | 削除・順序・一度きり・重心 |
| 逸脱 | 予想・安全・約束事・既視 |
| 視点 | 視点・時制・信頼 |
| 不在 | 分岐・沈黙・欠落 |
| 熱量 | 熱量・密度 |
| 調子 | 調子・笑い・落差 |
| 具体 | 固有・感覚 |

**調子の群を足したのは実測から。** 喜劇の原稿を読ませたところ、
当時18あった観点の**どれも可笑しみに触れなかった**。
調子を扱う問いが一つも無かったため。

一度に渡すのは2〜3個までにする。**3Bモデルでは指示を増やすと
一つひとつが薄まる**ことを実測している(禁止語6個は効いたが8個では効かなくなった)。
多く見たいなら、数を増やすのではなく `--all` で回すか、種を変えて何度か回す。

## 語の取り出し方 (`--words`)

反復を探すときの語の切り出し。既定は正規表現(漢字2文字以上か
カタカナ2文字以上)で、依存が無く手元だけで動く。

```bash
python main.py read 第五稿.txt --words 形態素     # fugashi + unidic-lite が要る
```

```bash
pip install fugashi unidic-lite
```

**既定を正規表現のままにしている理由。** 参考作品で素直に差し替えて測ると、
反復が68件から178件に膨れ、雑音(しょっちゅう・だんだん・いっぱい)が増え、
`虫干し` が `虫/干し` に割れて**作者の伏線を落とした**。正解は4/7から3/7へ下がる。

一方で拾い物もある。一文字の名詞(鴻・毛・羽)が取れるようになり、
「あっちゃぐり」では `スーパー[8]・[84]・[88]` — **安売りスーパーと
「スーパーエンジニア」の二重**を検出した。

どちらが良いかは原稿による。**比べて要らなければ
`centurion/connect.py` の `morphological_words` ごと消せばよい。**

## 検査 — 答えを鵜呑みにしない

`--api` / `--run` のときは自動で走る。貼って答えを得た場合は `check` で。

```bash
python main.py check 答え.txt 第五稿.txt --chunk 1 --out 添削.txt
```

三つを見る。

| 検査 | 見つかるもの |
|---|---|
| 段落番号の実在 | 存在しない番号への指摘 |
| 渡した範囲 (`--chunk N`) | 読ませていない段落への言及 |
| 引用と本文の照合 | 番号と中身が食い違う指摘、本文に無い文の引用 |

照合するのは**10文字以上の鉤括弧**だけにしてある。日本語は語をそのまま
「あっちゃぐり」のように括るので、短いものまで突き合わせると
**正しい指摘に × が付く**。実際に作中語を括った指摘3件へ誤って × を付けていた。
見落とすほうが、良い指摘を捨てるより安全という判断。

## 検証 — 別のモデルに検分させる

```bash
python main.py ask 第五稿.txt --llama --verify
python main.py ask 第五稿.txt --llama --verify --verify-with api
python main.py ask 第五稿.txt --api --verify --verify-model claude-opus-5
```

| 引数 | 既定 | 意味 |
|---|---|---|
| `--verify` | — | 出てきた指摘をもう一度検分させ、通ったものだけ残す |
| `--verify-with` | 同じ経路 | 検分を別の経路にやらせる (`api` / `llama` / `run`) |
| `--verify-model` | 同じモデル | 検分に使うモデル |

**機械の照合では届かないところを見る。** 引用と本文の突き合わせで捕まるのは
「引用が食い違う」までで、**引用は正しいが判断が的外れ**な指摘は素通りする。
Qwen の実測で引用14件中8件が取り違えだったとき、残る6件が良い指摘だという
保証はどこにもなかった。

設計は Phase 9 の教訓に従っている。

- **点数を付けさせない。** 絶対評価は基準が回ごとに19pt動いて使い物にならない。
  一件ずつ「残す」か「捨てる」かの二択にする
- **疑う側に立たせる。** 「良いところを探して」と頼めば全部が残る。
  粗を探す側に置き、**迷ったら捨てる**のを既定にする
- **別のモデルに検分させたほうが効く。** 同じモデルは自分の答えを通しがちになる

捨てる基準は、本文に無いことを言っている / 読み違えている /
何をどう直すのか分からない / 代償を書いていない / 他と同じことを言っている。

二つの安全弁がある。

- **全部捨てられたら元の答えを残す。** 検分が働きすぎている疑いがあるため
- **判定が読めなかった指摘は捨てずに残し、印を付ける。**
  検証が働かなかったことを、捨てたことにすり替えない

時間と費用は倍になる。

# 引数の一覧

`read` `ask` `check` は同じ引数を共有する。命令が違うだけで中身は一つ。

```bash
python main.py ask -h        # 実物の一覧はこれで出る
```

## 1. どの原稿を読ませるか

| 引数 | 既定 | 意味 |
|---|---|---|
| (原稿) | — | ファイル名かパス。**省くと窓が開く**(手元は選択、Colab はアップロード)。`manuscripts/` に置いたものはファイル名だけでよい |

## 2. どこを読ませるか

長い原稿は塊に切ってから渡す。モデルの読める量に限りがあるため。

| 引数 | 既定 | 意味 |
|---|---|---|
| `--size N` | 6000 | 1塊の上限文字数 |
| `--chunk N` | 1つ目 | 何番目の塊を読ませるか |
| `--all` | — | 全部の塊を順に読ませる。塊ごとに観点が入れ替わる(発想・査読のみ) |
| `--verify` | — | 出てきた指摘をもう一度検分させ、通ったものだけ残す |
| `--verify-with` | 同じ経路 | 検分を別の経路にやらせる |
| `--verify-model` | 同じモデル | 検分に使うモデル |

```bash
python main.py ask 第五稿.txt --size 3000 --chunk 2
python main.py ask 第五稿.txt --all --api
```

## 3. 何を訊くか

| 引数 | 既定 | 意味 |
|---|---|---|
| `--mode 発想` | 発想 | まだ書かれていない先を探させる |
| `--mode 査読` | | 客観的に評価・査読させる |
| `--mode 接続` | | 遠く離れた二箇所に橋を架けさせる(**3000文字以上**) |
| `--mode 連想` | | 連想を数歩たどって作品へ戻させる |
| `--note "…"` | なし | 作者からの補足。狙いや訊きたいこと |

```bash
python main.py ask 第五稿.txt --mode 査読 --note "語り手の距離感を試しています"
```

## 4. どの観点で訊くか (発想・査読)

既定は原稿を実測して、足りていないところへ問いを向ける。

| 引数 | 既定 | 意味 |
|---|---|---|
| `--lenses N` | 3 | 一度に渡す観点の数。**2〜3を勧める**(増やすと一つひとつが薄まる) |
| `--lens 視点,熱量` | — | 観点を名指しする。測定を無視する |
| `--random-lenses` | — | 原稿を測らず、くじ引きで選ぶ |
| `--survey` | — | 何が測られ、どの観点が選ばれるかだけを出す |

観点の名前は「モードと観点」の表を参照。

## 5. モードごとの調整

| 引数 | 既定 | 効くモード | 意味 |
|---|---|---|---|
| `--top N` | 5 | 接続 | 候補の上位いくつから対を選ぶか |
| `--dream` | — | 接続 | 夢の作業(圧縮・移動・視覚化・後付け)を一つ添える |
| `--steps N` | 4 | 連想 | 連想を何歩たどらせるか |

```bash
python main.py ask 第五稿.txt --mode 接続 --top 3 --dream
python main.py ask 第五稿.txt --mode 連想 --steps 6
```

## 6. 誰に解かせるか

何も付けなければ**プロンプトを出すだけ**でモデルを呼ばない。

| 引数 | 既定 | 意味 |
|---|---|---|
| `--api` | — | Claude の API に解かせる。鍵は環境変数 `ANTHROPIC_API_KEY` から読む |
| `--llama` | — | 立ててある llama-server に解かせる。**AMDのGPUでも動く** |
| `--llama-url URL` | `http://127.0.0.1:8080/v1/chat/completions` | llama-server の窓口 |
| `--run` | — | 手元(か Colab)の transformers に解かせる。NVIDIAのGPUが要る |
| `--model 名` | api: `claude-sonnet-5` / run: `Qwen/Qwen2.5-3B-Instruct` | 使うモデル。`--llama` のときは記録のためだけ |
| `--tokens N` | 4000 | 答えの長さの上限。解かせるときだけ効く |

```bash
python main.py ask 第五稿.txt --api --model claude-opus-5
python main.py ask 第五稿.txt --llama --model LFM2.5-1.2B-JP
python main.py ask 第五稿.txt --run --model LiquidAI/LFM2-1.2B
```

| 解かせ方 | GPU | 費用 | 質 |
|---|---|---|---|
| `--api` | 不要 | かかる | 高い |
| `--llama` | AMD可 / CPUでも | 無料 | モデル次第 |
| `--run` | NVIDIA | 無料 | モデル次第 |
| 何も付けない | 不要 | 無料 | 貼る先のモデル次第 |

## 7. 結果をどうするか

| 引数 | 既定 | 意味 |
|---|---|---|
| `--out 添削.txt` | — | 本文の各段落の下に指摘を貼った添削ファイルを書く。日付・モード・モデル・観点も先頭に残る |
| `--check 答え.txt` | — | 答えのファイルを読み、段落番号と引用を検査する(`check` 命令が使う) |
| `--list` | — | 塊と反復の一覧だけを出す(`read` 命令が使う) |

外で解かせた答えを検査するときは、`--model` に何を使ったかを渡せる。
`不明` の代わりに `名 (申告)` として添削ファイルに残る。

```bash
python main.py check 答え.txt 第五稿.txt --out 添削.txt --model claude-opus-5
```

#### 左の数字が何を表しているか

| | 測っているもの |

## 原稿を読む

小説の校正・アイデア出しに向けた土台。モデルを使わないので、
GPUが無くても動く。

```bash
python main.py read 原稿.txt --size 6000
```

```
「冒頭プロトタイプ 第五稿」
  4533文字 / 見た目 8835 / 1章 / 103段落 / 218文
    0. (見出しなし)                      4311文字  103段落

3000文字ずつに切ると 2塊
  塊0: 0章 段落0〜70 (2977文字)
  塊1: 0章 段落71〜102 (1587文字、うち重なり1段落)
```

- 文字コードは utf-8 / Shift_JIS / EUC-JP を自動で判別
- 章の見出し(`# 見出し`、`第一章`、`＊` のような区切り)を拾う
- 青空文庫形式は凡例・底本の記録・ルビ・傍点の指定を落とし、題と著者を拾う
- 空行で区切る書き方と、1行1段落の書き方の両方に対応
- 会話文をまたがずに文へ分ける(「行こう。」と言った。→ 2文)

```python
from centurion.manuscript import Manuscript

manuscript = Manuscript.load("原稿.txt")
for chunk in manuscript.chunks(size=6000, overlap=1):
    print(chunk)                    # 塊3: 2章 段落58〜79 (5940文字)
    chunk.text                      # 重なりを含む、モデルに渡す本文
    chunk.body                      # 重なりを除いた、この塊が担当する部分
```

**塊は必ず位置を持ち歩く。** 校正では指摘が原稿のどこを指すかが本体なので、
章・段落の通し番号・原稿全体での文字位置を落とさない。
`manuscript.text[p.start:p.end] == p.text` が全段落で成り立つことを
試験で確かめている(ルビを落とす設定のときは、位置は落とした後の本文に対応)。

## 遠い二つを繋ぐ

発想の中身。ここもモデルを使わない。

Phase 5〜10 で5つの機構を作って、どれも跳躍を生まなかった。
共通していたのは**一本の生成を横へずらそうとしていた**ことである。
跳躍は一点の摂動ではなく二点の関係で、ずらしても繋ぐ相手がいなければ跳ばない。

だから相手を用意する。しかも**原稿の中から**取る。
外から奇抜な要素を持ち込めば提案は奇を衒ったものになるが、
[12]の止まった時計と[87]の折れた傘の骨を繋げと言えば、
提案は作者自身の世界の内側に留まる。
**プロンプトには対を選べない。原稿を全部持っている道具には選べる。**

```python
from centurion.connect import recurrences, distant_pairs
from centurion.manuscript import Manuscript

manuscript = Manuscript.load("原稿.txt")

for item in recurrences(manuscript)[:10]:
    print(item)     # 《反復》「虫干」[15]・[62] (隔たり75%)

for pair in distant_pairs(manuscript, count=5):
    print(pair)     # [23] × [86] (隔たり61% / 重なり0%)
```

**反復** … 稀な語が遠く離れて二度以上使われている箇所。作者がすでに植えた種。
回数が少なければ仕掛け、多ければ作品の背骨として分けて示す。

**遠い対** … 語彙を共有しない遠い二点。まだ架かっていない橋。

繋ぎ方は `build_connection_prompt`(二点に橋を架けさせる)と
`build_chain_prompt`(連想を数歩たどって作品へ戻させる)の二つ。
夢の作業を操作に置き換えた `DREAM_WORK`(圧縮・移動・視覚化・後付け)も
併せて渡せる。

### 効いていることの確かめ方

正解の分かっている作品 — 作者が意図して遠い二点を結んだもの — で試した。
**無作為に対を選ぶ方式は5回試して正解を0件しか拾えなかった**
(候補1165対から6個を引くので当然だった)。
稀な語の反復を手がかりにする方式に変えたところ、
作者が張った伏線が上位に出るようになり、
こちらが正解として数えていなかった接続まで挙がった。

分かっている限界:
- **短い作品には使えない。** 遠い二点が無いので何も出ない。
  実距離の下限を1500文字にしてある — 割合だけで測っていたときは、
  太宰治「I can speak」(1949文字・15段落)で「酔漢」が[8]と[12]に出て
  「隔たり27%」と表示されたが、実際には4段落しか離れておらず、
  同じ場面の同じ人物だった。繋がりはすでに本文にあり、架ける橋がない。
  目安として3000文字を切る原稿では、接続ではなく査読と発想を使う
- **一文字の語は拾えない。** 形態素解析を使っていないため、
  「鴻の鳥」の「鴻」のような一文字の要は落ちる
- **一度きりの語は長編でしか意味を持たない。**
  4500文字の抜粋では221語が該当し、証明・歴史・二日目まで拾ってしまう
- 一般語の除外は、実測で上位に来たものから作った小さな手作りの一覧に頼っている

## 論評と発想

原稿を読ませるための問いと、その組み立ては `centurion/review.py`。

査読と発想は規則が逆を向く。査読では「作品に無いものを言わない」が
幻覚を防ぐ正しい規則になるが、これは**アイデア出しと真っ向から衝突する**。
伴走AIはまだ書かれていないものを語るのが仕事だから。だからモードを分ける。

観点は願望ではなく**操作**として書く。
「独創的な意見を」と頼めば平板な答えが返る
(3Bでの実測では「感覚を書け」50%に対し「名前のある場所か人を置く」78%)。

```python
from centurion.review import build_prompt, check_citations, choose_lenses

lenses = choose_lenses(count=3)          # 群を散らして観点を選ぶ
head, body = build_prompt(chunk, lenses, mode="発想", title=manuscript.title)

# 答えが実在する段落を指しているかを機械で確かめる
real, missing, outside = check_citations(answer, manuscript)
```

段落に番号を振って渡し、指摘を番号で示させる。
多くの査読プロンプトは「引用が実在するか確認せよ」とモデルに自己申告させるが、
番号なら**機械が確かめられる**。

### 実際に論評させる

```bash
python main.py ask 原稿.txt --mode 発想 --api        # その場で論評させる
python main.py ask 原稿.txt --mode 発想 --api --all  # 最初から最後まで
python main.py ask 原稿.txt --mode 接続 --api --dream
```

`--api` は Claude に解かせ、**答えの段落番号の検査まで自動で通す**。
鍵は環境変数 `ANTHROPIC_API_KEY` から読むだけで、この道具は保存も表示もしない。

```bash
setx ANTHROPIC_API_KEY "自分の鍵"      # Windows。設定後に端末を開き直す
```

`--all` は塊ごとに観点を入れ替える。全部の塊に同じ観点を当てると
同じ角度の指摘が並ぶだけになるため(Phase 9 の処方)。

`--run` にすると手元(か Colab)のモデルで解く。無料だが、
**3B級では論評の質が出ない**。

### 鍵を使わない道

```bash
python main.py read 原稿.txt                        # 塊と反復の一覧
python main.py ask 原稿.txt --mode 発想 > 問い.txt   # 問いを出す
#  問い.txt を好きなチャットへ貼り、答えを 答え.txt に保存してから
python main.py check 答え.txt 原稿.txt --chunk 1     # 段落番号を検査する
```

### 答えを検査する

`--api` / `--run` のときは自動で走る。貼って答えを得た場合は `check` で。

```bash
python main.py check 答え.txt 原稿.txt --out 添削.txt
```

三種類の誤りを見つける。

| 検査 | 見つかるもの |
|---|---|
| 段落番号の実在 | 存在しない番号への指摘 |
| 渡した範囲(`--chunk N`) | 読ませていない段落への言及 |
| **引用と本文の照合** | **番号と中身が食い違う指摘、本文に無い文の引用** |

三つ目が要る理由。Qwen2.5-3B に104段落の原稿を読ませたところ、
段落番号は**18件すべて実在して検査は素通り**した。ところが引用を突き合わせると、
**14件中8件が別の段落の中身**で、**うち3件は本文にどこにも無い文**だった。

```
× [58] 引用は [57] の中身: エーマートの前を通った。半分…
× [59] 本文に無い文を引用している: 帰る途中、エーマートの冷蔵庫…
```

「引用が実在するか確認せよ」とモデルに自己申告させても効かない。
申告する当人が取り違えているため。

### 添削ファイル

`--out 添削.txt` で、本文の各段落の下にその段落あての指摘を貼ったファイルを書く。
照合に落ちた指摘には `×` が付くので、信じてよいものと捨てるものが分かれる。

```
[58] アパートに帰り、電気もつけずに、私は部屋の真ん中に立っていた。
    × - **段落 [58]**: 「エーマートの前を通った。半分切れた看板が…」

[59] 座ればいいのに、と自分でも思う。布団はそこにある。座椅子もある。
    × - **段落 [59]**: 「帰る途中、エーマートの冷蔵庫の扉を開けると…」
```

## 分かっている限界

**目的の後半は達成していない。** 「文章を保つ」は抑圧で達成したが、
「発想の飛躍」は3つの機構を作って測って、いずれも読み手には届かなかった。
いま出てくるのは、読みやすく、常套からわずかに外れた文章であって、
飛躍ではない。

**随筆調に寄る。** 実測112件を数えるとこうなっている。

| | |
|---|---|
| 読み手に語りかける | 112/112 (100%) |
| 名前のある人や場所を含む | 2/112 (2%) |
| 過去の出来事を2文以上語る | 32/112 (29%) |
| 一文目が「Xは〜です」型の一般論 | 47/112 (42%) |

人格には「物語だけを愛する」と書いてあるのに、7割が出来事を語らない。
原因は書き出しの「そうですね、」だと見ている — 相槌のあとに文法的に
自然に続くのは同意・意見・一般化であって、場面ではない。
ただしこれは**未検証**なので、既定は評価時と同じ相槌のままにしてある。
`--prefill` で試せる。

**流動プロンプトの優位は確定していない。** p=0.108 で、有意水準には
届いていない。戻すなら `--fixed-prompt`。
